# RT persistence: 0.10.66

Verified on the user's VID 2233 / PID 006B keyboard on 2026-10-20.

## Failure and fix

The old application wrote the HE setting, read INIT25/26 to verify it, read ten
sections for a backup, then sent `08 F2` and reported success without receiving
any acknowledgement. The INIT reader filters unrelated input packets, including
the firmware's pending `00 C9` / `00 CA` cache-checksum request. Discarding this
request prevents completion of the save exchange. Reopening a HID handle did
not prove nonvolatile persistence.

The request is generated by the setting write itself, before `DRIVER_ED`:
`rt-crc-request-timing.json` records an unchanged-key write, receives `00 C9`
before sending `08 F2`, answers it with `08 C9 00 <tagLE>`, and receives `00 FE`.
The input queue must not be drained after a setting write. Earlier investigation
inferred that INIT cleared a firmware dirty flag; the observed lost CRC request
is the supported explanation. Firmware internals were not inspected.

0.10.66 takes backups before modifying HE settings. It answers CRC requests and
waits for SAVE_END before reading the profile for verification. The same sequence
covers individual keys, groups, Apply to all and HE JSON import. Group/import
batches commit before their existing batch verification, including restoration
on error. Silence, malformed reports and disconnection fail instead of producing
a false success. Repeated CRC requests receive the same tag.

## Original implementation

Target: MMPanel 4.9.7.0, SHA-256
`2537d9d620df12e51100c18ce9066d5dd38a01c38adf869d4d6925b78a9cd2fe`.
Protected method bodies were inspected in the restored analysis copy using IDA
and resolved IL; the restored executable was never run.

- QC64.NavigationViewModel.NAVI_OFF_SAVE_CMD, IDA `0x1891f0`: `08 F2`,
  enum DRIVER_ED. The argument 2000 belongs to an obfuscation guard, not a sleep.
- QC64.NavigationViewModel.HidRcvProc, `0x179aa0`: CRC handling and SAVE_END.
- TFdLn1YB0L, `0x189b90`: `[08, command, flag, crc32LE, ...]`.
- sRgQl3BT7I, `0x55e30`: non-reflected polynomial 04C11DB7, initial FFFFFFFF,
  little-endian words, zero-padding to a word, no final XOR.
- Original checksums identify its serialized host-cache files, rather than
  validating raw firmware records. This app uses the expected raw profile data
  as its own cache identity, excluding previous tags/padding. It always reads
  real profiles and does not use the vendor's cached files.
- `08 00 FE` finishes INIT; it is distinct from `08 F2`. Adding INIT_END alone
  did not fix persistence.

Passive original-app traces: `rt-vendor-startup-1792529192.json` (full INIT/cache
exchange) and `rt-vendor-startup-1792529291.json` (cache reuse). The observer
records some reads more than once through nested Windows APIs; duplicate log
entries are not evidence of duplicate USB traffic.

## Validation and limits

Regression tests model a CRC request queued by the setting write and lost by an
intervening INIT read. They cover individual/group/all-key order, native CRC
vectors, incomplete exchanges, stale completion, duplicate requests and errors.
Packaging tests and the Windows build passed. Packaged UI opened with 64 switches
and successfully read both M1 and M2 (`electron-built-result.json`).

The full test run had 359 passing assertions and six existing calibration UI
failures (outdated reload/timer mocks); its calibration worker retained a real
HID telemetry listener and was stopped after its assertions. Those 29 calibration
unit tests passed separately with hardware telemetry stubbed. These unrelated
fixtures and calibration behavior were not changed by this fix. Full output:
`rt-full-tests.txt`, `rt-calibration-isolated-tests.txt`.

The power-cycle result establishes the tested RT setting, not every lighting,
programming or calibration operation. Their existing generic save path has not
been reordered here; an unacknowledged save now produces an error. SAVE_END is
an acknowledgement for an individual operation, not a fresh power-cycle test.
